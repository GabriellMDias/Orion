# Approval Request Implementation Conventions

[Business specification](approval-request.md) · [Phase 3 plan](../implementation-plan.md#phase-3) · [Architecture and artifact workflow](../architecture/backend-execution-and-generated-artifacts.md)

This records the Phase 3 implementation details for the approved [Approval Request business rules](approval-request.md) and [H-05 access model](approval-request.md#identity-and-authorization-boundary). The Phase 5 server, schema, routes, and reference generators now exist. Business meaning remains in the specification; cross-cutting policy remains in the linked architecture, API, database, and security documents.

## Placement and ownership

- The initial backend feature belongs under `apps/api/src/features/approval-requests/`, with local domain rules, application operations, persistence adapter/port, transport contracts/routes, and colocated tests. These are responsibilities, not a mandatory file-by-file scaffold. The API composition root wires the feature. Fastify and token verification remain at trusted transport/infrastructure boundaries; domain behavior depends on neither Fastify nor Prisma. This follows [application boundaries](../architecture/application-boundaries.md), [dependency rules](../architecture/dependency-rules.md), [ADR-0004](../adr/0004-select-fastify-as-the-backend-http-framework.md), and [ADR-0006](../adr/0006-select-prisma-orm-for-database-access-and-migrations.md).
- The API application owns this feature's Prisma schema, migrations, and PostgreSQL persistence boundary under `apps/api/prisma/` until a real multi-application database ownership need exists. The Approval Request feature owns its table semantics and writes; other applications do not import API internals or access the table directly. The web feature lives in `apps/web` and consumes the generated API client, as required by [ADR-0007](../adr/0007-establish-api-contract-openapi-sdk-and-configuration-schema-strategy.md).
- Do not create `packages/domain/`, `packages/contracts/`, or `packages/database/` solely for this one backend consumer. Extract only when shared meaning or a genuine ownership boundary exists. `packages/sdk/` now owns the thin generated-client boundary used by the web app.

## Identity, identifiers, and time

- The feature owns one opaque, immutable request ID. The backend generates a random UUID for creation and uses that same value as the initial PostgreSQL primary key and public resource identifier; clients cannot choose it. The ID conveys no ownership or permission. If storage identity later changes, the public ID remains stable under [API identifier policy](../api/principles.md#identifiers) and [database identifier policy](../database/principles.md#identifiers).
- The trusted authentication boundary supplies a provider-independent, stable application principal ID. Creation stores that ID as immutable `creatorId`, the sole owner relationship. The API does not accept `creatorId` from the request body. Provider claim mapping belongs to the authentication adapter; it must preserve owner identity across provider changes rather than making domain data depend on raw OIDC claims. No tenant or admin key is added.
- Store `createdAt` and `updatedAt` as absolute instants in PostgreSQL `timestamptz`. PostgreSQL is the authoritative clock for both; set `createdAt` on insertion and advance `updatedAt` on each successful edit or state change using database time in the same write, rather than an ORM/application-clock convenience timestamp. Serialize as UTC RFC 3339 date-time strings at the API boundary. Neither browser time nor `updatedAt` is a concurrency token. Additional lifecycle timestamps are not required by the current business specification, and these two timestamps do not constitute an audit trail.

## Mutations, concurrency, and transactions

- Persist a positive integer `version`, initialized to `1`, and increment it exactly once for each successful draft edit or state transition. Every edit, submit, approve, reject, and cancel request carries the last observed `expectedVersion` as a typed contract field. A stale version is rejected; the server never silently retries it against a newer request version. Reads return the current version. `createdAt`/`updatedAt` are informational, not preconditions.
- A mutation must atomically condition its write on request ID, expected version, valid source state, and applicable owner or non-owner relationship. The trusted review capability is checked by the application using the verified principal. An affected-row count of zero requires safe classification as absent/hidden, stale, or invalid state without revealing unauthorized data. The version and state condition must be enforced by PostgreSQL, not only by a prior read. A real migrated-PostgreSQL test must prove two competing writes cannot both win, including edit versus submit and approve versus reject/cancel.
- The application operation owns each short PostgreSQL consistency boundary. Creation inserts the request and its idempotency identity atomically; each other operation commits its state, version, reason (when rejecting), and `updatedAt` together. Domain rules determine valid transitions without importing transaction APIs; the Prisma adapter executes the conditional persistence. No database transaction spans an identity-provider call or external effect. There is no default outbox, message, or business-audit write. See [transactions and concurrency](../database/transactions-and-concurrency.md) and [delivery and side effects](../architecture/delivery-and-side-effects.md).
- Creation requires a caller-generated opaque `Idempotency-Key` for one creation intent, scoped to the authenticated principal. Persist the key and a canonical intent fingerprint with the created request under a unique owner/key constraint in the same transaction. The same owner/key and same intent safely return the original request; the same key with different intent conflicts. Other state-changing operations use `expectedVersion`: an exact repeat after success is reported as a version or state conflict and cannot produce a second effect. The key is ordinary internal data and follows the request's eventual retention disposition. Do not infer a global idempotency service from this feature.

## Read and list contracts

- `get` returns an authorized request. Owners can read their requests in every state. The review view is limited to `SUBMITTED` requests owned by someone else, which are the requests currently relevant to a decision; a reviewer who also owns a request still sees it through owner access. A completed decision removes the request from this review view. Broader reviewer history would require an explicit business requirement and access decision.
- `list` has explicit `mine` and `reviewable` scopes, defaulting to `mine`. `reviewable` requires the trusted review capability and applies the same non-owner `SUBMITTED` predicate; a non-reviewer receives a denial. Authorized filtering must be enforced in the query before pagination. No unrestricted list exists.
- Both scopes use opaque cursor pagination ordered by `createdAt DESC, id DESC`, with default page size `20` and maximum `100`. A cursor is bound to the scope and filters, and its contents are not trusted as authorization evidence. Validate it and apply the current access predicate on every page. Inserts or state changes between pages may change membership; a cursor is not a snapshot guarantee. No arbitrary sort, search, or ORM-field filter is offered initially. This follows [API pagination policy](../api/principles.md#pagination).

## API failures and canonical metadata

Use the repository's [error envelope and registry policy](../api/error-contract.md). The [machine-readable registry](../../apps/api/src/errors.ts) and [executable TypeBox contracts](../../apps/api/src/features/approval-requests/contracts.ts) own exact declarations. Do not expose Prisma codes, SQLSTATE, request existence hidden by authorization, or provider claims.

| Condition | Public code | HTTP status |
| --- | --- | --- |
| Missing, expired, or invalid bearer access token | `AUTHENTICATION_REQUIRED` | `401` |
| Authenticated principal lacks review capability, attempts self-review, or requests `reviewable` without capability | `PERMISSION_DENIED` | `403` |
| Request absent or inaccessible by ID, including non-owner owner-only operations | `RESOURCE_NOT_FOUND` | `404` |
| Malformed contract input, missing/blank rejection reason, invalid cursor, or missing/invalid `expectedVersion`/idempotency key | `VALIDATION_FAILED` | `400` |
| Authorized operation from an invalid or terminal state | `APPROVAL_REQUEST_INVALID_STATE` | `409` |
| Authorized write based on a stale request version | `RESOURCE_VERSION_CONFLICT` | `409` |
| Reused creation key with different intent | `IDEMPOTENCY_KEY_REUSED` | `409` |

Check authentication and authorization before returning resource state or version details. A hidden resource and a nonexistent one share the same public not-found result. The application owns the feature-specific invalid-state meaning; shared error codes retain their [registry ownership](../api/error-contract.md#error-code-ownership). Error messages are safe explanatory text, not a machine contract. Exact successful response shapes and HTTP route paths belong to the executable TypeBox contracts and [generated OpenAPI](../generated/api/openapi.json).

The schema and adjacent semantic metadata describe the feature-owned request table and every column, including creator ID, opaque request ID, idempotency key/fingerprint, status, version, rejection reason, and timestamps. Use one structured metadata source adjacent to `apps/api/prisma/schema.prisma` for semantic descriptions, owning feature, `INTERNAL` classification, null meaning, clock/unit semantics, and non-obvious constraint/index purposes; do not copy column types or nullability that the migrated database already exposes. Document that rejection reason is absent outside `REJECTED`, creator identity is immutable, and version increments on successful mutation. Cross-check metadata object and field names against migrated PostgreSQL, including custom SQL objects, so missing or stale entries fail validation. Prisma Schema Language is the authored representation for what it can express, reviewed SQL migrations cover PostgreSQL details, and the **fully migrated PostgreSQL schema** is the complete physical truth. The reference is generated from or verified against that migrated schema, never maintained by hand. This follows [ADR-0006](../adr/0006-select-prisma-orm-for-database-access-and-migrations.md) and [schema documentation](../database/schema-documentation.md).

## Current Phase 5 contract

The Phase 5 executable contract defines `title` as required nonblank text up to 200 characters and `description` as optional supporting text up to 2,000 characters. A draft edit replaces both fields; omitting `description` clears it. Rejection requires nonblank `reason` up to 2,000 characters. These are contract limits, not new business states. The trusted JWT boundary requires a stable Orion UUID in `orion_principal_id`, requires `orion_actor_type=human`, and maps the `approval:review` OAuth scope to the provider-independent capability. A future provider must supply that mapping without changing stored ownership. The API uses a single PostgreSQL statement as the atomic transaction boundary for create or conditional mutation; the conditional update checks ID, version, source state, and owner/non-owner relationship in PostgreSQL. The migration CLI reads `ORION_MIGRATION_DATABASE_URL`; the runtime reads only `ORION_DATABASE_URL`. The [API runtime guide](../../apps/api/README.md) and [generated OpenAPI](../generated/api/openapi.json) provide current execution and wire details.

## Failure recovery and retry ownership

The current API, repository adapter, SDK, and web mutations do not automatically retry state-changing operations. The web query client also disables automatic read retries. A caller can initiate another request deliberately; there is no stacked retry policy or promise that a transport failure means the database did not commit. The PostgreSQL adapter uses one atomic insert or conditional update per operation. Its only extra read is after a unique-key collision on creation, to return the already committed request or classify a conflicting intent. It does not reissue the insert or a failed conditional update.

Creation is the only operation needing durable replay: the authenticated owner's `Idempotency-Key` and exact draft intent are committed with the request. If the response is lost, a same-owner retry with the same key and intent returns that request, including after process restart. Changing the intent under that key returns `IDEMPOTENCY_KEY_REUSED`. A new key is a new creation intent and may create another request; callers who lost the original key must inspect their authorized list before starting a new creation. This is scoped deduplication, not a global exactly-once guarantee.

Edit and state transitions use the observed `expectedVersion`. After a timeout, disconnect, or unexpected server failure, the caller must fetch the current request and reconcile its state/version before deciding on a new action. Blindly repeating an old version yields a conflict if the first write committed; a conflict does not by itself identify which caller won. The web UI gives operation-specific unknown-outcome guidance and offers a detail reload. A known validation, authorization, invalid-state, stale-version, or rate-limit response is classified by its stable error code; unexpected dependency exceptions yield one safe `INTERNAL_ERROR` diagnostic without logging raw exception content. A readiness failure is not proof that an earlier write did not commit.

Real migrated-PostgreSQL tests cover concurrent same-key creation, conflicting key reuse, stale edits and submissions, competing terminal outcomes, repeat submission, a caller deadline after a committed creation, and failed-statement rollback. The emitted-process smoke forcibly stops the API after a committed decision and verifies recovery and creation replay from a new process. No feature operation has an external side effect to compensate or describe as transactionally reversible.

The approved feature has no automatic deletion or legal retention duration, no authoritative business-audit persistence requirement, and no external delivery or integration requirement. Therefore this phase adds no deletion worker, derived-copy reconciliation, audit table, outbox/inbox, or compensation workflow. This does not authorize indefinite production retention: the actual retention/disposal policy remains an owner and operations decision before production use under [H-09](../human-actions.md#h-09) and [data retention](../security/data-retention.md). Application data currently resides in PostgreSQL; browser Query data is transient and cleared when the bearer token changes. Logs, traces, errors, and metrics retain only the existing allowlisted operational fields; request bodies, credentials, arbitrary URLs, exception messages, and event attributes are excluded from export. Metric dimensions are bounded to method, status, route template, and network protocol fields.
