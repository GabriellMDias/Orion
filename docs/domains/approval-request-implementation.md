# Approval Request Implementation Conventions

[Business specification](approval-request.md) · [Phase 3 plan](../implementation-plan.md#phase-3) · [Architecture and artifact workflow](../architecture/backend-execution-and-generated-artifacts.md)

This records the Phase 3 implementation details for the approved [Approval Request business rules](approval-request.md) and [H-05 access model](approval-request.md#identity-and-authorization-boundary). It is an implementation design, not a claim that applications, schemas, routes, or generators exist. Business meaning remains in the specification; cross-cutting policy remains in the linked architecture, API, database, and security documents.

## Placement and ownership

- The initial backend feature belongs under `apps/api/src/features/approval-requests/`, with local domain rules, application operations, persistence adapter/port, transport contracts/routes, and colocated tests. These are responsibilities, not a mandatory file-by-file scaffold. The API composition root wires the feature. Fastify and token verification remain at trusted transport/infrastructure boundaries; domain behavior depends on neither Fastify nor Prisma. This follows [application boundaries](../architecture/application-boundaries.md), [dependency rules](../architecture/dependency-rules.md), [ADR-0004](../adr/0004-select-fastify-as-the-backend-http-framework.md), and [ADR-0006](../adr/0006-select-prisma-orm-for-database-access-and-migrations.md).
- The API application owns this feature's Prisma schema, migrations, and PostgreSQL persistence boundary under `apps/api/prisma/` until a real multi-application database ownership need exists. The Approval Request feature owns its table semantics and writes; other applications do not import API internals or access the table directly. The future web feature lives in `apps/web` and consumes the generated API client, as required by [ADR-0007](../adr/0007-establish-api-contract-openapi-sdk-and-configuration-schema-strategy.md).
- Do not create `packages/domain/`, `packages/contracts/`, or `packages/database/` solely for this one backend consumer. Extract only when shared meaning or a genuine ownership boundary exists. `packages/sdk/` becomes useful when the web consumer is implemented.

## Identity, identifiers, and time

- The feature owns one opaque, immutable request ID. The backend generates a random UUID for creation and uses that same value as the initial PostgreSQL primary key and public resource identifier; clients cannot choose it. The ID conveys no ownership or permission. If storage identity later changes, the public ID remains stable under [API identifier policy](../api/principles.md#identifiers) and [database identifier policy](../database/principles.md#identifiers).
- The trusted authentication boundary supplies a provider-independent, stable application principal ID. Creation stores that ID as immutable `creatorId`, the sole owner relationship. The API does not accept `creatorId` from the request body. Provider claim mapping belongs to the authentication adapter; it must preserve owner identity across provider changes rather than making domain data depend on raw OIDC claims. No tenant or admin key is added.
- Store `createdAt` and `updatedAt` as absolute instants in PostgreSQL `timestamptz`. PostgreSQL is the authoritative clock for both; set `createdAt` on insertion and advance `updatedAt` on each successful edit or state change using database time in the same write, rather than an ORM/application-clock convenience timestamp. Serialize as UTC RFC 3339 date-time strings at the API boundary. Neither browser time nor `updatedAt` is a concurrency token. Additional lifecycle timestamps are not required by the current business specification, and these two timestamps do not constitute an audit trail.

## Mutations, concurrency, and transactions

- Persist a positive integer `version`, initialized to `1`, and increment it exactly once for each successful draft edit or state transition. Every edit, submit, approve, reject, and cancel request carries the last observed `expectedVersion` as a typed contract field. A stale version is rejected; the server never silently retries it against a newer request version. Reads return the current version. `createdAt`/`updatedAt` are informational, not preconditions.
- A mutation must atomically condition its write on request ID, expected version, valid source state, and applicable owner or non-owner relationship. The trusted review capability is checked by the application using the verified principal. An affected-row count of zero requires safe classification as absent/hidden, stale, or invalid state without revealing unauthorized data. The version and state condition must be enforced by PostgreSQL, not only by a prior read. A real migrated-PostgreSQL test must prove two competing writes cannot both win, including edit versus submit and approve versus reject/cancel.
- The application operation owns each short PostgreSQL consistency boundary. Creation inserts the request and its idempotency identity atomically; each other operation commits its state, version, reason (when rejecting), and `updatedAt` together. Domain rules determine valid transitions without importing transaction APIs; the Prisma adapter executes the conditional persistence. No database transaction spans an identity-provider call or external effect. There is no default outbox, message, or business-audit write. See [transactions and concurrency](../database/transactions-and-concurrency.md) and [delivery and side effects](../architecture/delivery-and-side-effects.md).
- Creation requires a caller-generated opaque `Idempotency-Key` for one creation intent, scoped to the authenticated principal. Persist the key and a canonical intent fingerprint with the created request under a unique owner/key constraint in the same transaction. The same owner/key and same intent safely return the original request; the same key with different intent conflicts. Other state-changing operations use `expectedVersion`: an exact repeat after success is reported as a version or state conflict and cannot produce a second effect. The key is ordinary internal data and follows the request's eventual retention disposition. Do not infer a global idempotency service from this feature.

## Read and list contracts

- `get` returns an authorized request. Owners can read their requests in every state. The review view is limited to `SUBMITTED` requests owned by someone else, which are the requests currently relevant to a decision; a reviewer who also owns a request still sees it through owner access. A completed decision removes the request from this review view. Broader reviewer history would require an explicit business requirement and access decision.
- `list` has explicit `mine` and `reviewable` scopes, defaulting to `mine`. `reviewable` requires the trusted review capability and applies the same non-owner `SUBMITTED` predicate; a non-reviewer receives a denial. Authorized filtering must be enforced in the query before pagination. No unrestricted list exists.
- Both scopes use opaque cursor pagination ordered by `createdAt DESC, id DESC`, with default page size `20` and maximum `100`. A cursor is bound to the scope and filters, and its contents are not trusted as authorization evidence. Validate it and apply the current access predicate on every page. Inserts or state changes between pages may change membership; a cursor is not a snapshot guarantee. No arbitrary sort, search, or ORM-field filter is offered initially. This follows [API pagination policy](../api/principles.md#pagination).

## API failures and canonical metadata

Use the repository's [error envelope and registry policy](../api/error-contract.md). These are planned semantic mappings; the future machine-readable registry and executable schemas own exact declarations once implemented. Do not expose Prisma codes, SQLSTATE, request existence hidden by authorization, or provider claims.

| Condition | Public code | HTTP status |
| --- | --- | --- |
| Missing, expired, or invalid bearer access token | `AUTHENTICATION_REQUIRED` | `401` |
| Authenticated principal lacks review capability, attempts self-review, or requests `reviewable` without capability | `PERMISSION_DENIED` | `403` |
| Request absent or inaccessible by ID, including non-owner owner-only operations | `RESOURCE_NOT_FOUND` | `404` |
| Malformed contract input, missing/blank rejection reason, invalid cursor, or missing/invalid `expectedVersion`/idempotency key | `VALIDATION_FAILED` | `400` |
| Authorized operation from an invalid or terminal state | `APPROVAL_REQUEST_INVALID_STATE` | `409` |
| Authorized write based on a stale request version | `RESOURCE_VERSION_CONFLICT` | `409` |
| Reused creation key with different intent | `IDEMPOTENCY_KEY_REUSED` | `409` |

Check authentication and authorization before returning resource state or version details. A hidden resource and a nonexistent one share the same public not-found result. The application owns the feature-specific invalid-state meaning; shared error codes retain their [registry ownership](../api/error-contract.md#error-code-ownership). Error messages are safe explanatory text, not a machine contract. Exact successful response shapes and HTTP route paths belong to executable TypeBox contracts and route metadata when Phase 5 creates them; this table prevents ambiguity in failure semantics without inventing a second contract source.

The future schema and adjacent semantic metadata must describe the feature-owned request table and every column, including creator ID, opaque request ID, idempotency key/fingerprint, status, version, rejection reason, and timestamps. Use one structured metadata source adjacent to `apps/api/prisma/schema.prisma` for semantic descriptions, owning feature, `INTERNAL` classification, null meaning, clock/unit semantics, and non-obvious constraint/index purposes; do not copy column types or nullability that the migrated database already exposes. Document that rejection reason is absent outside `REJECTED`, creator identity is immutable, and version increments on successful mutation. Cross-check metadata object and field names against migrated PostgreSQL, including custom SQL objects, so missing or stale entries fail validation. Prisma Schema Language is the authored representation for what it can express, reviewed SQL migrations cover PostgreSQL details, and the **fully migrated PostgreSQL schema** is the complete physical truth. The reference is generated from or verified against that migrated schema, never maintained by hand. This follows [ADR-0006](../adr/0006-select-prisma-orm-for-database-access-and-migrations.md) and [schema documentation](../database/schema-documentation.md).

## Verification handoff

Later phases must test the authorization matrix with synthetic principals, all listed errors at the HTTP boundary, create-key replay/conflict, conditional updates against real migrated PostgreSQL, cursor authorization and ordering, and generated-artifact freshness. These checks do not exist yet. [Phase 4](../implementation-plan.md#phase-4) builds only the API foundation; persistence and the full feature belong to later phases.
